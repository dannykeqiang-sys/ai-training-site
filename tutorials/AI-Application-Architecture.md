# AI 应用架构模式

构建 AI 应用不只是调用一个 API。本文介绍常见的 AI 应用架构模式，帮助你理解不同产品形态背后的技术选择。


## 一、三种常见产品模式

![Chatbot、Agent、Copilot 三种产品模式](https://yk-ai-mentor.youku.com/yk_ai_mentor/tutorials/ch1/images/ai-product-modes_1784688757.png)

### 1.1 Chatbot（聊天机器人）

**定义**：用户通过对话与 AI 交互，AI 逐轮生成回复。

**典型场景**：客服机器人、问答助手、闲聊机器人

**架构特点**：
- 单轮或多轮对话
- 每轮调用一次 LLM
- 需要维护对话历史（Context Window）
- 通常结合 RAG 提供领域知识

```
用户消息 → [对话历史管理] → [RAG 检索] → LLM → 回复
```

**关键挑战**：
- 对话历史管理（避免 Context Window 溢出）
- 多轮一致性（避免"遗忘"早期对话内容）
- 响应延迟（用户期望秒级响应）

### 1.2 Agent（智能体）

**定义**：AI 自主规划、调用工具、迭代执行，直到完成目标。

**典型场景**：代码助手、数据分析 Agent、自动化工作流

**架构特点**：
- 多步骤执行（Plan → Act → Observe → Reflect）
- 工具调用（Function Calling / MCP）
- 自主决策（LLM 决定下一步行动）
- 可能需要人工确认（Confirmation Gates）

```
用户目标 → [规划] → [工具调用] → [观察结果] → [反思] → 循环直到完成
```

**关键挑战**：
- 工具设计（单一职责、清晰描述）
- 错误恢复（工具调用失败怎么办）
- 成本控制（多轮调用可能很贵）
- 安全性（防止 Prompt Injection）

### 1.3 Copilot（副驾驶）

**定义**：AI 作为人类的辅助，提供建议但不自主执行。

**典型场景**：代码补全、文档写作助手、设计建议

**架构特点**：
- 人类主导，AI 辅助
- 实时建议（如代码补全的 Ghost Text）
- 人类决定是否接受建议
- 通常不需要工具调用

```
人类工作 → AI 实时观察 → AI 生成建议 → 人类接受/拒绝
```

**关键挑战**：
- 低延迟（建议需要在毫秒级出现）
- 上下文理解（理解人类当前在做什么）
- 建议质量（避免干扰而非帮助）

### 1.4 三种模式对比

| 维度 | Chatbot | Agent | Copilot |
|---|---|---|---|
| **自主性** | 低（被动回复） | 高（主动执行） | 低（被动建议） |
| **工具调用** | 可能（RAG） | 必需 | 通常不需要 |
| **人工介入** | 每轮 | 关键节点 | 每步 |
| **延迟要求** | 秒级 | 分钟级可接受 | 毫秒级 |
| **成本** | 中 | 高 | 低 |
| **典型模型** | GPT-4、Claude | GPT-4、Claude | 专用小模型 |


## 二、开源 vs 闭源模型选型

### 2.1 开源模型（Open-Weight Models）

**代表**：LLaMA、Mistral、Qwen、DeepSeek

**优势**：
- **隐私**：数据不出企业网络，适合敏感场景
- **可定制**：可以微调、修改架构
- **成本可控**：无 API 调用费，只有硬件成本
- **无供应商锁定**：可以自由切换部署环境

**劣势**：
- **能力上限**：通常弱于最强闭源模型
- **运维成本**：需要自己管理 GPU、推理服务
- **更新滞后**：新特性需要等待社区发布

**适用场景**：
- 数据敏感（医疗、金融、政务）
- 高频调用（API 费用过高）
- 需要深度定制（微调、架构修改）
- 离线环境（无法访问外网）

### 2.2 闭源模型（Proprietary APIs）

**代表**：GPT-4、Claude、Gemini

**优势**：
- **最强能力**：通常代表当前最先进水平
- **零运维**：无需管理基础设施
- **快速迭代**：供应商持续更新
- **生态丰富**：工具链、文档、社区支持

**劣势**：
- **隐私风险**：数据发送到外部服务器
- **成本不可控**：高频调用费用高昂
- **供应商锁定**：难以切换
- **延迟**：网络往返 + 排队等待

**适用场景**：
- 需要最强能力（复杂推理、创意生成）
- 低频调用（成本可控）
- 快速原型（不想管理基础设施）
- 非敏感数据

### 2.3 选型决策树

```
数据是否敏感（医疗、金融、政务）？
├── 是 → 开源模型（本地部署）
└── 否 → 调用频率如何？
         ├── 高频（>1000 次/天）→ 开源模型（成本可控）
         └── 低频（<1000 次/天）→ 闭源 API（最强能力 + 零运维）
```

### 2.4 混合架构

很多生产系统采用**混合架构**：

```
简单任务 → 开源小模型（本地，低延迟，低成本）
复杂任务 → 闭源大模型（API，最强能力）
```

**典型模式**：
- **路由层**：根据任务复杂度选择模型
- **降级策略**：闭源 API 不可用时切换到开源模型
- **成本优化**：简单任务用小模型，复杂任务用大模型


## 三、流式输出（Streaming）

### 3.1 为什么需要流式输出

LLM 生成文本是**逐 token 生成**的，完整响应可能需要数秒甚至数十秒。如果等待完整响应再返回，用户体验很差。

**流式输出**（Streaming）：服务端逐 token 推送，客户端实时显示。

**优势**：
- **降低感知延迟**：用户立即看到第一个 token，感觉"很快"
- **提升用户体验**：像打字一样逐字出现，更自然
- **支持中断**：用户可以中途停止生成

### 3.2 技术实现：SSE（Server-Sent Events）

**SSE** 是流式输出的标准协议：

```
客户端 → 服务端：POST /chat/completions (stream: true)
服务端 → 客户端：data: {"choices": [{"delta": {"content": "你"}}]}
服务端 → 客户端：data: {"choices": [{"delta": {"content": "好"}}]}
服务端 → 客户端：data: {"choices": [{"delta": {"content": "！"}}]}
服务端 → 客户端：data: [DONE]
```

**关键特性**：
- 单向推送（服务端 → 客户端）
- 基于 HTTP（无需 WebSocket）
- 自动重连（浏览器原生支持）

### 3.3 架构影响

流式输出对架构有以下影响：

| 组件 | 影响 |
|---|---|
| **API 网关** | 需要支持长连接、禁用响应缓冲 |
| **负载均衡** | 需要会话粘性（同一连接路由到同一后端） |
| **后端服务** | 需要异步处理、逐 token 生成 |
| **前端** | 需要 EventSource API、增量渲染 |

**常见陷阱**：
- ❌ Nginx 默认缓冲响应 → ✅ 配置 `proxy_buffering off`
- ❌ 负载均衡随机路由 → ✅ 配置会话粘性
- ❌ 前端等待完整响应 → ✅ 使用 EventSource 逐 token 渲染


## 四、RAG 架构模式

![RAG 架构演进：基础 → Advanced → Agentic](https://yk-ai-mentor.youku.com/yk_ai_mentor/tutorials/ch1/images/rag-arch-evolution_1784688824.png)

### 4.1 基础 RAG

```
用户查询 → [Embedding] → [向量检索] → [检索结果] → [拼接到 Prompt] → LLM → 回复
```

**适用场景**：简单问答、知识库检索

**局限**：
- 检索质量依赖 Embedding 和向量库
- 无法处理复杂查询（需要多步推理）
- 可能检索到不相关内容

### 4.2 Advanced RAG

```
用户查询 → [查询改写] → [多路检索] → [重排序] → [检索结果] → LLM → 回复
```

**增强技术**：
- **查询改写**：用 LLM 改写用户查询，提升检索质量
- **多路检索**：同时检索多个数据源（向量库 + 关键词库）
- **重排序**：用 Cross-Encoder 对检索结果重新排序
- **上下文压缩**：只保留检索结果中最相关的部分

**适用场景**：复杂问答、多源知识融合

### 4.3 Agentic RAG

```
用户查询 → [Agent 规划] → [工具调用：检索] → [观察结果] → [反思：够不够] → 循环
```

**增强技术**：
- **Agent 自主决策**：Agent 决定是否需要检索、检索什么
- **迭代检索**：检索结果不够时，Agent 自主发起新一轮检索
- **工具组合**：检索 + 计算 + 代码执行

**适用场景**：复杂分析、多步推理、需要验证的场景


## 五、总结

**产品模式选择**：
- **Chatbot**：对话交互、问答场景
- **Agent**：自主执行、复杂任务
- **Copilot**：实时辅助、人类主导

**模型选型**：
- **开源模型**：数据敏感、高频调用、需要定制
- **闭源 API**：需要最强能力、低频调用、快速原型
- **混合架构**：简单任务用小模型，复杂任务用大模型

**流式输出**：
- 降低感知延迟、提升用户体验
- 基于 SSE 协议实现
- 需要调整 API 网关、负载均衡、前端渲染

**RAG 架构**：
- **基础 RAG**：简单问答
- **Advanced RAG**：查询改写 + 多路检索 + 重排序
- **Agentic RAG**：Agent 自主决策、迭代检索
