# 上下文工程与窗口管理

随着 AI 编码工具从单轮问答进化到自主执行复杂任务的 Agent，如何为模型提供"恰好足够"的上下文信息成为关键挑战。本文讲解项目级知识持久化的必要性、Context Engineering 的核心理念，以及为什么不能简单地将整个代码库塞入上下文窗口。

## 一、为什么需要项目级知识持久化

### 1.1 问题背景

AI 编码工具中的大模型本质上是**无状态的**——每次对话都是独立的推理过程，模型不会自动"记住"上一次对话的内容。[¹](#ref1)

这导致一个现实问题：**项目级的知识和规则无法跨会话保持**。

| 场景 | 没有持久化时 | 有持久化时 |
|---|---|---|
| 编码规范 | 每次都要重复告诉 AI "用 4 空格缩进、函数名驼峰" | 一次写入规则文件，所有会话自动遵守 |
| 项目架构 | 每次都要解释"我们用的是 monorepo + 微服务" | AI 自动读取架构说明 |
| 技术栈约束 | AI 可能用 React 但项目要求 Vue | 规则文件约束技术栈选择 |
| 团队约定 | 代码审查标准、提交信息格式等每次重复 | 一次定义，团队共享 |

### 1.2 项目级知识持久化的本质

主流 AI 编码工具都提供了**项目级知识持久化机制**——在项目根目录放置规则文件，每次会话启动时自动注入到上下文中。[²](#ref2) [³](#ref3)

> 💡 **本质**：项目规则文件是自动注入到每次对话上下文中的持久化 System Prompt 片段。[²](#ref2)

## 二、Context Engineering 的定义与核心目标

![Context Engineering：多源信息的筛选与压缩](https://yk-ai-mentor.youku.com/yk_ai_mentor/tutorials/ch1/images/context-engineering-sources_1784689124.png)

### 2.1 定义

**Context Engineering（上下文工程）** 是一门研究如何在有限的上下文窗口中，为 LLM 精心筛选、组织和排列信息的学科，目标是让模型在每次推理时获得恰好足够的高质量信息。[⁴](#ref4)

它涵盖：
- 系统指令（System Prompt）
- 用户输入（User Prompt）
- 检索到的外部知识（来自知识库的 RAG 结果）
- 历史对话记录（Memory）
- 工具定义列表（Tools）
- 持久化规则（CLAUDE.md / Rules）

### 2.2 Context Engineering vs Prompt Engineering

| 维度 | Prompt Engineering | Context Engineering |
|---|---|---|
| **关注范围** | 单条指令/提示词的措辞 | 模型每次推理时接收的**全部信息**的设计 |
| **时间跨度** | 单轮对话 | 多轮对话、跨会话、整个 Agent 生命周期 |
| **核心技能** | 写出清晰明确的指令 | 构建数据获取管道、状态管理、Token 预算分配 |
| **适用场景** | 简单问答 | 复杂 Agent 应用、多步骤工作流 |

> Prompt Engineering 是 Context Engineering 的**子集**——前者只管"怎么说"，后者管"说什么、什么时候说、在哪里说、说多少"。[⁴](#ref4)

### 2.3 核心目标

Context Engineering 的核心目标是：[⁴](#ref4) [⁵](#ref5)

> **在有限的上下文窗口内，为模型提供"在正确时间、以正确方式、恰好足够"的信息，使其能做出最优决策。**

具体而言：
1. **最大化信息质量**：确保上下文中每个 Token 都是高价值的
2. **避免信息过载**：太多无关信息会稀释关键信息的注意力权重
3. **维护时效性**：过时信息可能误导模型决策
4. **控制成本**：Token 消耗直接决定 API 成本和响应延迟

## 三、为什么不能简单地将整个代码库塞入上下文

![全量塞入 vs 按需检索](https://yk-ai-mentor.youku.com/yk_ai_mentor/tutorials/ch1/images/context-why-not-all_1784689124.png)

即使模型的 Context Window 足够大（如 200K tokens），将整个代码库全部塞入上下文仍然是一个**糟糕的策略**：[¹](#ref1) [⁴](#ref4) [⁵](#ref5)

### 3.1 四大原因

| 原因 | 详细说明 |
|---|---|
| **1. 成本爆炸** | API 按 Token 计费。一个中型项目（10 万行代码）约 300 万 tokens，按 GPT-4o 价格（$2.50/1M input tokens）每次调用约 $7.5，完全不可承受 |
| **2. "Lost in the Middle" 效应** | 研究论文证明：模型对上下文**中间部分**信息的召回率显著低于开头和结尾，呈 U 型曲线[⁶](#ref6)。塞入越多内容，关键信息被"淹没"的概率越大 |
| **3. 注意力稀释** | 大量无关代码会稀释模型对关键代码的注意力权重。10 万行代码中可能只有 200 行与当前任务相关，其余 99.8% 都是"噪音" |
| **4. 延迟不可接受** | 输入 10 万 Token 的处理时间大约是 1 万 Token 的 10 倍（理论上 Transformer 复杂度为 O(n²)，实际通过 KV-Cache 等优化有所缓解），响应时间从几秒变成几十秒 |

### 3.2 "Lost in the Middle" 论文关键发现

Stanford 等机构 2023 年发表的论文 *"Lost in the Middle: How Language Models Use Long Contexts"* 发现：[⁶](#ref6)

```
召回准确率
  ^
  |  ■■                              ■■
  |    ■                            ■
  |      ■                        ■
  |        ■■■■■■■■■■■■■■■■■■■■
  |
  └──────────────────────────────────→ 信息在上下文中的位置
     开头        中间部分          结尾
```

- 关键信息放在**开头**或**结尾**时，模型召回率最高
- 放在**中间位置**时，召回率可能下降 20-40%
- 这个现象在不同模型和不同 Context Window 大小下**普遍存在**

> **场景化例子**：你在一个 10 万 Token 的上下文中，把一段关键 API 密钥放在第 5 万 Token 的位置，模型可能完全忽略它。但如果把同样的密钥放在上下文的开头或结尾，模型就能正确引用。

> ⚠️ 实践建议：将最重要的上下文（如当前正在编辑的代码、用户的核心需求）放在上下文的**开头或结尾**，避免放在中间。

### 3.3 正确的做法：精准检索 + 渐进式加载

| 策略 | 说明 |
|---|---|
| **代码检索（Code Search）** | 根据当前任务，用语义搜索或关键词搜索找到最相关的代码片段，只注入这些片段 |
| **分层加载** | 先加载文件结构概览 → 用户确认后加载具体文件 → 需要时再加载依赖文件 |
| **摘要压缩** | 对历史对话进行摘要，用简短总结替代完整的对话记录 |
| **工具输出裁剪** | 截断过长的工具返回值，只保留关键信息 |
| **相关性过滤** | 使用评分模型或阈值过滤掉相关性低的检索结果 |
| **位置优化** | 将最关键的信息放在上下文的开头和结尾 |

### 3.4 真实场景：上下文管理的好坏对比

**场景**：用户要求"修复订单服务中的金额计算 Bug"

**效果对比**：

| 指标 | ❌ 糟糕管理（塞入整个代码库） | ✅ 良好管理（精准注入相关文件） |
|---|---|---|
| Token 消耗 | 100,000 | 8,000 |
| 响应时间 | 30+ 秒 | 2-3 秒 |
| 单次成本 | ~$1.00 | ~$0.05 |
| Bug 定位准确率 | ~40% | ~90% |


## 四、各工具的上下文管理策略

| 工具 | 核心理念 | 上下文控制方式 | 适合场景 | Token 效率 |
|---|---|---|---|---|
| **Claude Code** | 自动检索 + 渐进加载 | 自动检测相关文件，无需手动指定 | 通用开发，"开箱即用" | 高 |
| **Cursor** | 用户主动控制 + @ 引用 | 通过 @文件名、@代码符号 显式引用 | 精确控制，明确知道需要哪些文件 | 高 |
| **Cline** | Agent 自主探索 | Agent 自主使用 read_file/list_files/search_files 工具 | 探索性任务，不确定需要哪些文件 | 中（可能过度探索） |

> 💡 **选择建议**：希望"少操心"选 Claude Code，希望"精确控制"选 Cursor，面对"探索性任务"选 Cline。


## 五、上下文质量评估

### 5.1 定量指标

| 指标 | 目标值 | 说明 |
|---|---|---|
| **上下文利用率** | > 70% | 上下文中与当前任务相关的 Token 占比 |
| **响应时间** | < 5 秒 | 从用户提问到模型开始输出的时间 |
| **单次成本** | < $0.10 | 单次 API 调用的 Token 成本 |
| **重试率** | < 10% | 因上下文不足导致需要重新提问的比例 |

### 5.2 常见问题诊断

| 现象 | 原因 | 解决 |
|---|---|---|
| 模型频繁询问"X 是什么？" | 上下文中缺少 X 的定义或相关代码 | 将相关文件加入上下文 |
| 模型编造不存在的函数/API | 上下文中没有实际代码，模型只能猜测 | 检索并注入实际代码文件 |
| 模型输出冗长、不够聚焦 | 上下文中有太多无关信息，稀释注意力 | 减少噪音，只保留高相关信息 |
| 响应时间过长 | 上下文 Token 数过多 | 使用摘要压缩、截断工具输出 |


## 常见误解


- ❌ "CLAUDE.md 可以让模型学到新知识"——它只是临时注入到上下文，不改变模型权重

- ❌ "Context Engineering 就是写好的 Prompt"——Prompt Engineering 只是其子集
- ❌ "目标是尽可能多给模型信息"——过多信息反而降低模型表现

- ❌ "因为 Context Window 不够大"——即使窗口够大，上述四个问题仍然存在
- ❌ "因为代码是机密不能发送"——这是安全问题，不是上下文管理问题
