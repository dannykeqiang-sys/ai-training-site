# 提示工程

## 一、一句话定义

**Prompt Engineering（提示工程）** 是研究如何设计和优化提示词（Prompt），以系统性引导模型生成高质量输出的方法论。[¹](#ref1) [²](#ref2)
> 它绝不仅仅是"把话说清楚"那么简单，而是包含多种经典技巧的系统性方法。——ATA 内部资料 [¹](#ref1)

## 二、为什么需要 Prompt Engineering
大语言模型的工作本质是"概率性文字接龙"——给定输入序列，预测下一个最可能的 Token。这意味着：

1. **相同意图，不同表达 → 不同结果**：措辞、结构、示例的差异会显著影响输出质量。
2. **模型无法读心**：如果 Prompt 模糊，模型只能"自由发挥"，结果可能偏离预期。
3. **Token 成本可控**：好的 Prompt 能用更少的对话轮次、更低的 Token 消耗，获得更高质量的输出。
4. **Vibe Coding 的核心技能**：在 AI 辅助编程时代，Prompt Engineering 是与 AI 高效协作的基础能力。

| 场景 | 差 Prompt | 好 Prompt |
|------|-----------|-----------|
| 写代码 | "写一个排序函数" | "用 Python 实现快速排序算法，要求：支持自定义比较函数，包含 docstring 和类型注解" |
| 翻译 | "翻译这段话" | "将以下英文翻译为中文，保持技术术语不翻译（如 API、Token），语气正式" |
| 分析 | "分析这个问题" | "从性能、可维护性、安全性三个维度分析以下架构方案的优缺点，以表格形式输出" |
> 模型的能力是固定的，但 Prompt 的质量决定了你能**释放多少**模型能力。

### Prompt Engineering 与 Fine-tuning 的区别

Prompt Engineering 和 Fine-tuning 是两种不同的模型适配方式：
- **Prompt Engineering**：不改模型权重，只优化输入，即时生效，成本低，灵活性高
- **Fine-tuning**：更新模型权重，需要训练周期，成本高，适合深度定制

> 关于 Prompt Engineering vs Fine-tuning 的详细对比（适用场景、决策框架、典型场景对照），参见教程《Fine-tuning、SFT、PEFT 与 LoRA》。

## 三、六大核心策略

![提示工程六大核心策略](https://yk-ai-mentor.youku.com/yk_ai_mentor/tutorials/ch1/images/prompt-six-strategies_1784688878.png)

OpenAI 官方 Prompt Engineering 指南归纳了六大策略：[²](#ref2)
| # | 策略 | 核心思想 |
|---|------|----------|
| 1 | **Write clear instructions（写清晰的指令）** | 告诉模型你想要什么，而不是不想要什么 |
| 2 | **Provide reference text（提供参考文本）** | 给模型"开卷考试"的材料，减少幻觉 |
| 3 | **Split complex tasks into simpler subtasks（拆解复杂任务）** | 分而治之，降低单次请求难度 |
| 4 | **Give the model time to "think"（给模型思考时间）** | 引导逐步推理（CoT），提升准确率 |
| 5 | **Use external tools（使用外部工具）** | 让模型调用代码执行器、搜索引擎等弥补短板 |
| 6 | **Test changes systematically（系统性测试变更）** | 用评估集（Eval Set）量化每次改动的效果 |

### 技巧分类与选择

| 技巧 | 说明 | 适用场景 |
|------|------|----------|
| **Zero-shot** | 直接给出指令，不提供示例 | 模型能力强、任务简单时 |
| **Few-shot** | 在指令后提供若干输入-输出示例 | 需要统一格式或规则复杂时 |
| **Chain-of-Thought (CoT)** | 引导模型展示中间推理步骤 | 数学、逻辑、复杂决策 |
| **Role Prompting** | 在 System Prompt 中设定角色 | 需要特定专业深度或语言风格 |
| **结构化 Prompt** | 使用 Markdown/XML/JSON 组织内容 | Prompt 复杂、多模块时 |
> Zero-shot、Few-shot、CoT 的详细原理和示例见教程《提示技巧：角色、方法与链式推理》。
**如何选择技巧**：

```
任务是否需要推理/计算？
  ├── 是 → 使用 CoT（加入"请一步步思考"）
  │         └── 效果不够？→ Few-shot CoT（给带推理步骤的示例）
  └── 否 → 任务格式是否复杂/非标？
            ├── 是 → Few-shot（给 2-3 个示例）
            └── 否 → Zero-shot（直接指令）
                      └── 效果不佳？→ 添加角色设定 + 结构化约束
```

## 四、好 Prompt 的五个特征
结合 ATA 内部资料和 OpenAI/Anthropic 官方指南，高质量 Prompt 应具备以下特征：[¹](#ref1) [²](#ref2) [³](#ref3)

| 特征 | 说明 |
|------|------|
| **清晰（Clear）** | 指令明确无歧义，模型不需要"猜"你的意图 |
| **具体（Specific）** | 包含足够的约束条件和细节 |
| **结构化（Structured）** | 不同模块用分隔符明确划分 |
| **有上下文（Contextual）** | 提供完成任务所需的背景信息 |
| **有格式要求（Formatted）** | 明确指定输出的形式和结构 |

> **一句话总结**：好的 Prompt = 说清楚你要什么 + 给够必要信息 + 指定输出格式。
### 4.1 清晰指令

好的 Prompt 一定是**完整的、清晰的、明确的**。如果你只是简单地说"帮我写一首诗"，模型可能给你写古诗，也可能写现代诗，甚至可能来一首打油诗。

| 模糊 Prompt（差） | 清晰 Prompt（好） |
|-------------------|-------------------|
| "帮我写一首诗" | "请用五言绝句的格式，写一首以'春天的西湖'为主题的诗，要求押韵" |
| "总结这篇文章" | "请用 3 个要点总结以下文章的核心观点，每点不超过 30 字" |
| "写段代码" | "用 Python 3.10 写一个函数，输入一个列表，返回其中所有偶数的平方和" |

**实践要点**：
1. **说具体你要什么，而不是不要什么**："不要写太长" → "控制在 100 字以内"
2. **提供完成任务所需的所有信息**："分析这个数据" → "分析以下销售数据，找出 Q3 同比增长最快的品类"
3. **指定角色、受众、语气**："用通俗易懂的语言，面向没有技术背景的产品经理解释"

### 4.2 使用分隔符
分隔符（Delimiters）用来**明确划分不同信息模块边界**，使模型能够清楚区分"哪些是指令、哪些是数据、哪些是上下文"。[¹](#ref1) [⁴](#ref4)

| 分隔符类型 | 示例 | 特点 |
|-----------|------|------|
| **XML 标签** | `<context>...</context>` | Anthropic 推荐，结构最清晰 |
| **三引号** | `"""..."""` | 简洁，适合包裹文本块 |
| **三反引号** | ` ```...``` ` | 适合代码块 |
| **Markdown 标题** | `### 指令` / `### 上下文` | 直观易读 |

**核心价值**：
- 防止指令混淆——模型不会把数据内容误解为操作指令
- 降低 Prompt Injection 风险——外部内容被明确标记为"数据"
- 使用 XML 标签结构化 Prompt 可以产生比纯文本 Prompt **20-40% 更一致的输出** [⁴](#ref4)

### 4.3 指定输出格式
如果不指定格式，模型会按自己的"偏好"来组织输出，导致下游系统无法稳定解析。

| 格式 | 使用场景 | Prompt 中的指定方式 |
|------|----------|---------------------|
| **JSON** | API 集成、数据提取 | "以 JSON 格式返回，包含以下字段：..." |
| **表格（Markdown）** | 对比分析、数据展示 | "以 Markdown 表格形式呈现，列包括：..." |
| **编号列表** | 步骤说明、要点总结 | "用编号列表列出，每点不超过 20 字" |

**最佳实践**：给出模板或示例 + 约束长度和条目数 + 指定语言。

### 4.4 避免歧义

常见的歧义包括指代不清（如"分析它"）、标准模糊（如"写得好一点"）和范围不明（如"总结文章"）。消除歧义的方法：量化约束、给出标准、提供反例、指定范围、拆分任务。

### 4.5 提供上下文信息
上下文信息是指完成任务所需的**背景知识、限定条件和参考材料**。

| 类型 | 说明 | 示例 |
|------|------|------|
| **任务背景** | 任务产生的原因和目标 | "这是一份面向新员工的入职指南" |
| **领域知识** | 专业术语定义或业务规则 | "在我们公司，SKU 指的是..." |
| **受众信息** | 输出面向谁 | "读者是没有技术背景的管理层" |
| **约束条件** | 必须遵守的限制 | "不得提及竞品名称" |
> ⚠️ 上下文并非越多越好。过多会导致"中间信息丢失"（Lost in the Middle）现象。**最重要的指令和上下文应放在 Prompt 的开头或结尾**。

## 五、综合实践：一个完整的高质量 Prompt

```xml
<role>
你是一位高级数据分析师，擅长从销售数据中提取业务洞察。
</role>
<context>
我们是一家电商公司，拥有 2024 年 Q3 各品类销售数据，目标是找出增长最快的品类以加大投入。
</context>
<task>
分析以下数据，找出 Q3 同比增长率最高的 3 个品类，并给出增长原因假设。
</task>
<data>
品类A：Q3 2023 销售额 500万，Q3 2024 销售额 800万
品类B：Q3 2023 销售额 300万，Q3 2024 销售额 420万
品类C：Q3 2023 销售额 200万，Q3 2024 销售额 380万
</data>
<output_format>
以 Markdown 表格形式输出，列包括：品类名称、同比增长率、可能的增长原因。
按增长率从高到低排序。
</output_format>
```

## 六、迭代优化最佳实践

![Prompt 迭代优化闭环](https://yk-ai-mentor.youku.com/yk_ai_mentor/tutorials/ch1/images/prompt-iteration-loop_1784688872.png)

### 核心理念

Prompt Engineering 的本质是**实验科学**——没有人能一次写出完美的 Prompt。OpenAI 和 Anthropic 都强调：[²](#ref2)

> "Test changes systematically."——系统性地测试每一次改动，而不是凭感觉调整。

### 迭代流程

```
[定义目标] → [编写初版 Prompt] → [测试代表性用例]
     ↑                                      ↓
     └── [分析失败案例] ← [评估输出质量] ←──┘
```

### 实践要点

| 原则 | 说明 |
|------|------|
| **从简单开始** | 先写最简 Prompt，观察模型表现，再逐步添加约束 |
| **单次只改一个变量** | 便于归因——分清是指令、示例还是格式导致了改善/退化 |
| **建立评估集** | 准备 10-20 条覆盖正常/边界/对抗场景的测试用例 |
| **量化对比** | 用准确率、格式匹配率等客观指标衡量，避免主观判断 |
| **版本管理** | 生产环境的 Prompt 应纳入版本控制（Git），支持回滚 |

## 常见误解

- ❌ "Prompt Engineering 就是把需求说清楚"——远不止于此，还包括系统性测试和迭代
- ❌ "Prompt Engineering 是训练模型"——不改变模型权重，只优化输入
- ❌ "Prompt 越短越好"——清晰度比长度更重要
- ❌ "分隔符只是为了让人类阅读方便"——它直接影响模型的解析
- ❌ "指定格式会限制模型的创造力"——格式约束的是形式，不是内容质量
- ❌ "好的 Prompt 应该一次写成"——这违背了 PE 的核心理念
- ❌ "上下文越多越好"——过多会导致信息过载和"中间信息丢失"
