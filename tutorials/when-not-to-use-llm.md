# 何时不该用大模型

大模型能力强大且持续进化，但这不意味着每个问题都应该用大模型解决。本文帮助你建立判断框架，在大模型和传统方案之间做出最优选择。


## 一、核心判断框架

![该不该用大模型的决策树](https://yk-ai-mentor.youku.com/yk_ai_mentor/tutorials/ch1/images/when-not-llm-decision_1784688774.png)

选择工具时，考虑四个维度：

| 维度 | 关键问题 |
|---|---|
| **确定性** | 是否需要 100% 可预测、可复现的结果？ |
| **成本效率** | 这个任务的调用频率和预算约束是什么？ |
| **可审计性** | 是否需要完整的决策追溯和合规证明？ |
| **复杂度** | 问题是否有明确的规则或公式？ |

### 决策树

```
任务是否有明确的规则/公式/标准？
├── 是 → 传统方案通常更优（确定性高、成本低、易审计）
└── 否 → 问题复杂度如何？
         ├── 简单模式识别 → 传统 ML 可能更高效
         └── 需要理解自然语言/复杂推理 → 大模型是正确选择
```


## 二、传统方案更优的场景

### 2.1 需要确定性和可审计性

| 场景 | 为什么传统方案更优 | 推荐方案 |
|---|---|---|
| **金融交易逻辑** | 需要 100% 确定性 + 完整审计链 | 业务规则引擎 + 参数化查询 |
| **医疗诊断决策** | 法律责任 + 可解释性要求 | 临床决策支持系统 + 人工审核 |
| **航空/核电控制** | 安全关键系统不允许概率性 | 形式化验证 + 确定性算法 |
| **财务对账** | 需要精确到分的可追溯计算 | 数据库事务 + 对账脚本 |

**关键洞察**：这些场景不是大模型"做不到"，而是传统方案在**确定性、可审计性、法律责任**上更优。

### 2.2 高频调用且成本敏感

| 场景 | 大模型方案成本 | 传统方案成本 | 推荐 |
|---|---|---|---|
| **邮箱格式验证**（百万次/天） | ~$50/天 API 费用 | ~$0.01/天 正则计算 | 正则表达式 |
| **日期计算**（高频） | 累积成本可观 | 几乎为零 | `datetime` 库 |
| **简单分类**（结构化数据） | 大模型推理成本高 | XGBoost 推理成本低 100x | 传统 ML |
| **实时推荐**（毫秒级响应） | LLM 延迟 1-3 秒 | 协同过滤 <10ms | 专用推荐模型 |

**关键洞察**：大模型能完成这些任务，但**成本效率**差距可能达到 100-1000 倍。

### 2.3 规则明确且稳定

| 场景 | 大模型方案 | 传统方案 | 推荐 |
|---|---|---|---|
| **税务计算** | 可能算错 + 需要验证 | 税率表 + 公式 = 100% 准确 | 规则引擎 |
| **权限校验** | 需要大量 Prompt 工程 | RBAC/ABAC 模型清晰明确 | 权限框架 |
| **数据格式转换** | 可能遗漏边界情况 | ETL 工具经过充分测试 | 数据处理管道 |

**关键洞察**：当规则**明确、稳定、可枚举**时，硬编码比"教大模型理解规则"更可靠。


## 三、大模型更适合的场景

### 3.1 需要理解自然语言

- **文档总结**：理解长文档并提取关键信息
- **多语言翻译**：处理语义、文化差异、上下文
- **代码解释**：将技术概念转化为易懂的语言
- **创意写作**：生成营销文案、故事、对话

### 3.2 需要处理非结构化数据

- **图像理解**：描述图片内容、识别物体（多模态模型）
- **音频转录**：语音识别 + 语义理解
- **文档解析**：从 PDF、扫描件中提取结构化信息

### 3.3 需要复杂推理和生成

- **代码生成**：根据需求描述生成完整功能
- **数据分析**：理解业务问题并生成 SQL/Python 分析代码
- **问题解决**：多步骤推理、方案设计、创意生成

### 3.4 需要快速原型和探索

- **概念验证**：快速实现想法，验证可行性
- **数据探索**：交互式分析，发现数据中的模式
- **学习辅助**：解释概念、生成示例、回答问题


## 四、混合方案：最佳实践

![大模型 + 传统方案的混合架构](https://yk-ai-mentor.youku.com/yk_ai_mentor/tutorials/ch1/images/hybrid-llm-pattern_1784688892.png)

很多生产系统采用**混合架构**，结合大模型和传统方案的优势：

### 4.1 大模型生成 + 传统验证

```
用户需求 → 大模型生成代码/SQL/配置 → 传统工具验证（测试、语法检查、规则校验）→ 执行
```

**示例**：
- 大模型生成 SQL → ORM 执行 + 结果验证
- 大模型生成代码 → 单元测试 + 静态分析 + Code Review
- 大模型生成配置 → Schema 验证 + 安全扫描

### 4.2 路由分层：简单任务用传统方案，复杂任务用大模型

```
用户请求 → [复杂度判断] → 简单任务 → 传统方案（低成本、快速）
                        → 复杂任务 → 大模型方案（高能力、灵活）
```

**示例**：
- 客服系统：FAQ → 关键词匹配；复杂问题 → LLM
- 代码助手：变量补全 → 专用小模型；架构设计 → 大模型
- 数据分析：简单聚合 → SQL 模板；复杂分析 → LLM 生成代码

### 4.3 大模型辅助 + 人工决策

```
大模型提供建议/草稿/分析 → 人工审核 → 人工决策 → 执行
```

**适用场景**：
- 高风险决策（医疗、法律、金融）
- 创意工作（品牌策略、设计方向）
- 战略决策（投资、招聘、产品方向）


## 五、常见误区

### 5.1 "大模型什么都能做，所以应该用大模型"

**误区**：大模型能力强大，所以所有任务都应该用大模型。

**现实**：能力强大不等于**成本效率最优**。就像用超级计算机算 1+1 是浪费，很多简单任务用传统方案更快、更便宜、更可靠。

**正确思维**：选择**最适合**的工具，而非**最强大**的工具。

### 5.2 "传统方案过时了"

**误区**：大模型时代，正则表达式、规则引擎、传统 ML 都是"老技术"。

**现实**：这些技术经过几十年验证，在特定场景下仍然是最优解。技术的价值不在于新旧，而在于**是否适合当前问题**。

**正确思维**：新旧技术不是对立关系，而是工具箱中的不同工具。

### 5.3 "大模型不够准确，所以不能用"

**误区**：大模型有概率性，所以关键场景不能用。

**现实**：大模型的"不准确"可以通过**验证层**解决。大模型生成 + 传统验证 = 既有大模型的灵活性，又有传统方案的可靠性。

**正确思维**：不是"能不能用大模型"，而是"如何设计系统让大模型的输出可验证"。


## 六、决策检查清单

在选择大模型 vs 传统方案前，回答这些问题：

- [ ] 这个任务是否需要**100% 确定性**？（是 → 倾向传统方案）
- [ ] 这个任务的**调用频率**如何？（高频 → 考虑成本效率）
- [ ] 这个任务的**规则是否明确且稳定**？（是 → 倾向传统方案）
- [ ] 这个任务是否需要**理解自然语言或复杂推理**？（是 → 倾向大模型）
- [ ] 这个任务是否需要**快速原型或探索**？（是 → 倾向大模型）
- [ ] 这个任务的**失败成本**如何？（高 → 需要验证层或人工审核）


## 七、总结

**没有银弹**：大模型和传统方案各有优势，关键是选择最适合当前问题的工具。

**核心原则**：
1. **确定性优先**：需要 100% 可预测 + 可审计 → 传统方案
2. **成本敏感**：高频调用 + 预算约束 → 传统方案或混合方案
3. **复杂推理**：需要理解语言 + 灵活推理 → 大模型
4. **混合方案**：大模型生成 + 传统验证 = 最佳实践

**最终建议**：
- 不要因为大模型强大就过度使用
- 不要因为传统方案"老"就忽视
- 根据**确定性、成本、复杂度**做理性选择
- 生产系统优先采用**混合方案**：大模型的灵活性 + 传统方案的可靠性
