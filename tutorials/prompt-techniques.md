# 提示技巧：角色、方法与链式推理

本篇深入讲解提示工程中最核心的技巧：消息角色机制（System/User Prompt）、角色扮演（Role Prompting）、以及三种经典提示方法（Zero-shot、Few-shot、Chain-of-Thought）。掌握这些技巧能显著提升你使用 LLM 解决问题的效率和准确率。

## 一、消息角色：System Prompt 与 User Prompt

![System Prompt 与 User Prompt 的分工](https://yk-ai-mentor.youku.com/yk_ai_mentor/tutorials/ch1/images/system-user-prompt_1784688921.png)

### 1.1 Chat API 中的角色机制

现代 LLM 的 Chat API 采用**多角色消息数组**组织输入：[²](#ref2) [³](#ref3)

| 角色 | 说明 | 典型用途 |
|------|------|----------|
| **system** | 开发者配置的"元指令"，对用户不可见 | 定义角色、设定行为规则、约束输出格式 |
| **user** | 终端用户的实际输入 | 提问、下达具体任务指令 |
| **assistant** | 模型的历史回复 | 多轮对话中携带上下文 |

### 1.2 System Prompt 的作用

**System Prompt** 是开发者在后台配置的全局性指令，用于告诉模型"你是谁"以及"你应该按照什么规则做事"。它在整个对话过程中持续影响模型行为。[¹](#ref1)

| 维度 | 说明 | 示例 |
|------|------|------|
| **角色定义** | 告诉模型它是谁 | "你是一位资深 Java 架构师" |
| **行为边界** | 规定能做什么、不能做什么 | "只回答技术问题，拒绝政治相关问题" |
| **输出契约** | 规定输出格式 | "以 JSON 格式返回" |
| **安全约束** | 降低有害输出风险 | "如果不确定，请说'我不知道'" |

**重要限制**：
- System Prompt **影响**模型但**不能保证**完全遵守（尤其在对抗性输入下）
- 不同模型版本之间效果可能有差异
- 长对话中影响力可能逐渐减弱

### 1.3 System Prompt 与 User Prompt 的关系

> **核心比喻**：System Prompt 好比**公司制度手册**——规定员工的身份和行为准则；User Prompt 好比**客户具体需求单**——描述当下要解决的问题。

| 维度 | System Prompt | User Prompt |
|------|--------------|-------------|
| **设置者** | 开发者 | 终端用户 |
| **可见性** | 对用户不可见 | 对用户可见 |
| **生命周期** | 整个会话全程生效 | 每轮对话独立 |
| **职责** | 定义"模型是谁、怎么做" | 定义"模型做什么" |

**协作示例——客服机器人**：

System Prompt（用户不可见）：
```
你是"XX商城"的在线客服助手。
规则：
1. 只回答与商城购物、物流、退换货相关的问题
2. 退款金额超过 500 元时，回复"已转接人工客服"
3. 回答简洁，不超过 100 字
```

User Prompt（用户输入）：`我的订单三天了还没发货，怎么回事？`

模型在 System Prompt 约束下以客服身份回应，而不会给出与购物无关的回答。

## 二、Role Prompting（角色提示）

### 2.1 定义与典型用法

**Role Prompting** 是在 Prompt（通常是 System Prompt）中给模型设定一个具体的角色身份，使其以该角色的专业知识和行为模式来回答问题。[¹](#ref1)

```
你是一位资深 Java 架构师，有 15 年分布式系统开发经验。
请从架构设计的角度回答以下问题。
```

### 2.2 效果与原理

| 维度 | 未设角色 | 设定角色后 |
|------|---------|-----------|
| **专业深度** | 泛泛而谈 | 使用专业术语、给出深度分析 |
| **回答风格** | 通用口吻 | 符合角色身份的表达方式 |
| **关注重点** | 面面俱到 | 聚焦角色专业领域 |

**为什么有效**：通过设定角色，模型倾向于从训练数据中该角色相关的知识分布进行采样，而非从所有知识中随机挑选。

### 2.3 最佳实践

| 实践 | 说明 |
|------|------|
| 角色描述具体化 | "资深Java架构师，15年经验" 优于 "一个程序员" |
| 说明行为特征 | "回答时给出代码示例和性能分析" |
| 结合领域约束 | "只回答 Java/Spring 生态相关问题" |
| 放在 System Prompt 中 | 确保全会话生效，不被后续对话冲淡 |

## 三、三种核心提示方法

![Zero-shot、Few-shot 与 Chain-of-Thought 对比](https://yk-ai-mentor.youku.com/yk_ai_mentor/tutorials/ch1/images/shot-prompting-compare_1784688893.png)

### 3.1 总览

| 技巧 | 核心做法 | 复杂度 | 适用场景 |
|------|----------|--------|----------|
| **Zero-shot** | 直接给指令，不提供示例 | 最低 | 任务简单、模型能力强 |
| **Few-shot** | 指令 + 若干输入-输出示例 | 中等 | 需要统一格式或规则复杂 |
| **Chain-of-Thought (CoT)** | 引导模型展示中间推理步骤 | 较高 | 数学、逻辑、多步推理 |

这三种技巧是 Prompt Engineering 的**基石**。[¹](#ref1)

### 3.2 Zero-shot Prompting

**Zero-shot Prompting** 是直接给模型下达指令，**不提供任何示例**，完全依赖模型从预训练知识中理解任务并生成输出。[¹](#ref1)

```
请判断以下用户评论的情感倾向，只回答"正面"、"负面"或"中立"：

评论："这家餐厅的菜品味道不错，但服务员态度很差，等了半小时才上菜。"
```

| 优势 | 局限 |
|------|------|
| 最节省 Token | 对复杂/非常规任务效果不稳定 |
| 编写简单、迭代快 | 输出格式难以精确控制 |

**适用场景**：任务定义标准且清晰、使用能力较强的大模型、对输出格式要求不严格。

### 3.3 Few-shot Prompting

**Few-shot Prompting** 是在指令后面提供若干个（通常 2-5 个）**输入-输出示例**，让模型"照猫画虎"地学习任务模式。[¹](#ref1) [²](#ref2)

```
请将句子转换为JSON格式：

参考案例：
输入：张三，年龄25岁，职业工程师
输出：{"name": "张三", "age": 25, "job": "工程师"}

输入：李四，年龄30岁，职业设计师
输出：{"name": "李四", "age": 30, "job": "设计师"}

现在请处理：
输入：王五，年龄28岁，职业产品经理
输出：
```

Few-shot 利用的是 LLM 的**上下文学习（In-Context Learning）** 能力——无需更新权重，仅通过观察示例就能"临时学会"新的模式。[²](#ref2)

**示例选择原则**：

| 原则 | 说明 |
|------|------|
| **代表性** | 示例应覆盖任务的典型场景 |
| **多样性** | 示例间应有差异，覆盖不同情况 |
| **一致性** | 示例的格式和标注标准必须统一 |
| **适量** | 2-5 个通常足够，过多浪费 Token |

> 关键结论：示例的**质量比数量更重要**。3 个精心挑选的高质量示例，胜过 10 个随意堆砌的示例。

### 3.4 Chain-of-Thought Prompting

**Chain-of-Thought (CoT) Prompting** 引导模型在给出最终答案前**先展示中间推理步骤**，显著提升数学、逻辑、复杂决策等任务的准确率。[¹](#ref1) [³](#ref3)

**两种形式**：

**Few-shot CoT**（Wei et al. 2022）——在示例中包含推理步骤：

```
问：小明有 5 个苹果，给了小红 2 个，又买了 3 个，现在有几个？
答：让我们一步步思考。
    小明开始有 5 个苹果。
    给了小红 2 个，剩余 5 - 2 = 3 个。
    又买了 3 个，最终 3 + 3 = 6 个。
    答案是 6 个。

问：一个农场有鸡和兔共 35 只，脚共 94 只，鸡兔各几只？
答：
```

**Zero-shot CoT**——不提供示例，仅添加一句触发语：

```
一个农场有鸡和兔共 35 只，脚共 94 只，鸡兔各几只？

让我们一步一步思考。
```

这句 "Let's think step by step" 属于 **Zero-shot Chain-of-Thought** 技术——它不是 Few-shot（因为没有示例），而是 CoT 的一种零样本触发方式。[⁴](#ref4)

**CoT 为什么有效**：
1. 分解复杂问题为若干简单子问题
2. 暴露中间状态，形成推理链条
3. 减少"跳步"错误
4. 主要在**足够大的模型**（通常 >100B 参数）上有效 [³](#ref3)

| 适用 | 不适用 |
|------|--------|
| 数学计算和算术题 | 简单事实性问答 |
| 逻辑推理和判断 | 翻译等不需要推理的任务 |
| 多步骤决策问题 | 创意写作 |
| 代码调试和分析 | 对延迟敏感的实时场景 |

## 四、三种技巧的对比与组合

| 维度 | Zero-shot | Few-shot | CoT |
|------|-----------|----------|-----|
| **示例数量** | 0 | 2-5 个 | 0 或 2-5 个（含推理步骤） |
| **Token 消耗** | 最低 | 中等 | 最高 |
| **格式控制力** | 弱 | 强 | 中等 |
| **推理准确率** | 一般 | 一般 | 显著提升 |

**组合使用**：Few-shot + CoT（在示例中包含推理步骤）是解决复杂推理任务的黄金组合。

## 常见误解

- ❌ "System Prompt 可以保证模型绝对遵守指令"——它只是影响而非保证

- ❌ "Role Prompting 需要微调模型"——只需在 Prompt 中指定即可

- ❌ "Zero-shot 一定比 Few-shot 差"——对于强模型和简单任务，Zero-shot 可能就够了

- ❌ "Few-shot 需要重新训练模型"——不需要，这是推理时的技巧

- ❌ "CoT 是一种模型训练方法"——它是 Prompting 技巧

- ❌ "Few-shot Prompting"——没有提供示例，不是 Few-shot

- ❌ "示例数量越多效果越好"——过多浪费 Token，且可能引入噪音
