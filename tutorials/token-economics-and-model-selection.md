# Token 经济学与模型选型

调用 LLM API 不只是技术问题，也是经济问题。Token 怎么计费、不同模型价格差多少、什么时候该用什么模型——这些决策直接影响项目成本和产品质量。同时，LLM 作为"无状态系统"有一些工程上的固有局限，不理解这些局限就容易在生产环境中踩坑。


## 一、Token 计费模型

### 1.1 输入与输出分开计费

![Token 计费模型：输入、输出与缓存](https://yk-ai-mentor.youku.com/yk_ai_mentor/tutorials/ch1/images/token-pricing-model_1784688784.png)

LLM API 的计费基础是 **Token 数量**，但输入和输出的单价不同：[¹](#ref1)

| 计费项 | 说明 | 为什么不同 |
|--------|------|-----------|
| **Input Tokens** | 你发送给模型的所有内容（System Prompt + 历史对话 + 用户问题 + 工具描述） | 模型"读"的成本较低 |
| **Output Tokens** | 模型生成的回复内容 | 模型"写"的成本较高（需要逐 Token 推理） |

> **关键认知**：Output Token 的单价通常是 Input 的 **2~5 倍**。这意味着控制输出长度比控制输入长度更能省钱。

### 1.2 主流模型价格对比

以 2025 年主流模型为例（价格为每百万 Token 的美元价格）：[²](#ref2)

| 模型 | 输入价格 | 输出价格 | 定位 |
|------|---------|---------|------|
| **Claude Opus 4** | $15 | $75 | 旗舰推理，最贵最强 |
| **Claude Sonnet 4** | $3 | $15 | 性价比之选，日常开发主力 |
| **Claude Haiku 3.5** | $0.80 | $4 | 轻量快速，适合简单任务 |
| **GPT-4o** | $2.50 | $10 | 通用旗舰 |
| **GPT-4o-mini** | $0.15 | $0.60 | 低成本高频场景 |
| **Qwen-Plus** | ¥0.8/M | ¥2/M | 中文优化，性价比高 |

> **价格差异体感**：同一次对话（2000 input + 500 output tokens），Opus 花 $0.0675，Sonnet 花 $0.0135，Haiku 花 $0.0036——Opus 是 Haiku 的 **19 倍**。选型时务必匹配任务复杂度，不要"杀鸡用牛刀"。

### 1.3 隐性成本：被忽略的 Token 消耗

实际开发中，Token 消耗往往比预期高得多：[³](#ref3)

| 隐性消耗来源 | 说明 | 影响程度 |
|-------------|------|---------|
| **System Prompt** | 每次请求都发送，但开发者容易忽略 | 中等（几百到几千 tokens/次） |
| **工具描述** | MCP / Function Calling 的工具定义占用输入 | 高（复杂 Agent 可达数千 tokens） |
| **历史对话** | 多轮对话累积，每轮都重复发送 | 高（线性增长） |
| **RAG 检索结果** | 注入的外部知识片段 | 高（5~20 个片段，每个数百 tokens） |
| **思维链 / 推理过程** | 模型"思考"过程消耗输出 Token | 高（可能比最终回答多 3~10 倍） |

> **实例**：一次 Agent 任务（系统提示 500 tokens + 5 个工具定义 2000 tokens + 10 轮历史对话 5000 tokens + RAG 结果 3000 tokens）的输入就有 10,500 tokens。如果模型输出包含推理过程（2000 tokens 思考 + 500 tokens 回答），一次调用的总消耗约 13,000 tokens。


## 二、缓存机制：为什么同样的内容第二次更便宜

### 2.1 Prompt Caching（提示缓存）

主流 LLM API 提供 **Prompt Caching** 机制：如果多次请求中包含相同的前缀内容（如 System Prompt、工具定义），API 服务商会缓存这部分的处理结果，后续请求命中缓存时享受折扣。[⁴](#ref4)

```
第一次请求：
  System Prompt (500 tokens) + 工具定义 (2000 tokens) + 用户问题 → 全部正常计费

第二次请求（System Prompt 和工具定义不变）：
  System Prompt (500 tokens) ← 缓存命中，价格打折（通常 50%~90% 折扣）
  工具定义 (2000 tokens) ← 缓存命中，价格打折
  用户问题 (新问题) → 正常计费
```

| 提供商 | 缓存机制 | 折扣幅度 |
|--------|---------|---------|
| Anthropic | Prompt Caching（自动） | 缓存命中时输入价格 **降 90%** |
| OpenAI | Automatic Caching（自动） | 缓存命中时输入价格 **降 50%** |
| Google | Context Caching | 缓存命中时输入价格 **降 75%** |

> **工程启示**：设计 System Prompt 时，把**不变的内容放前面**（角色定义、工具定义），变化的内容放后面（用户问题），这样更容易命中缓存前缀。

### 2.2 KV Cache（推理缓存）

**KV Cache** 是模型推理层面的优化，开发者不直接操作，但理解它有助于理解 API 的延迟和成本行为：[⁵](#ref5)

- LLM 生成每个 Token 时，需要计算之前所有 Token 的 Key-Value 对（注意力机制的中间结果）
- KV Cache 把这些中间结果缓存下来，生成下一个 Token 时无需重算
- **对开发者的影响**：第一次生成（prefill）慢且贵，后续 Token 生成（decode）快且便宜

> 这就是为什么 API 的"首 Token 延迟"（Time to First Token）通常比后续 Token 的生成延迟高很多。


## 三、模型选型：不是越贵越好

### 3.1 模型能力维度

选择模型时，需要从多个维度评估：[⁶](#ref6)

| 维度 | 说明 | 典型差异 |
|------|------|---------|
| **推理能力** | 复杂逻辑、数学、多步推理 | 旗舰模型（Opus/GPT-4o）远强于轻量模型 |
| **代码能力** | 代码生成、理解、调试 | Claude 系列在代码任务上表现突出 |
| **上下文长度** | 能处理多长的文本 | 从 8K 到 1M+ tokens 不等 |
| **延迟** | 首 Token 延迟 + 生成速度 | 轻量模型通常快 3~10 倍 |
| **成本** | 每百万 Token 的价格 | 旗舰模型是轻量模型的 10~50 倍 |
| **多语言** | 中文、日文等非英文能力 | 各模型差异显著 |

### 3.2 模型定位矩阵

![模型定位矩阵：不是越贵越好](https://yk-ai-mentor.youku.com/yk_ai_mentor/tutorials/ch1/images/model-selection-matrix_1784688767.png)

不同模型有不同的"甜蜜区"：

| 模型 | 擅长 | 不擅长 | 典型使用场景 |
|------|------|--------|------------|
| **旗舰模型**（Opus、GPT-4o） | 复杂推理、架构设计、长文分析 | 贵、慢 | 核心业务逻辑、复杂重构、代码审查 |
| **中端模型**（Sonnet、GPT-4o-mini） | 日常编码、通用任务、性价比 | 极复杂推理可能出错 | 日常开发主力，80% 的场景 |
| **轻量模型**（Haiku、GPT-4o-mini） | 速度快、成本低、简单分类/提取 | 复杂任务质量下降 | 高频调用（分类、提取、格式化）、CI 中的自动化检查 |

### 3.3 选型决策框架

```
任务复杂度低 + 调用频次高 → 轻量模型（Haiku / Mini）
  例：日志分类、格式转换、简单提取

任务复杂度中 + 质量要求高 → 中端模型（Sonnet / GPT-4o）
  例：日常编码、Bug 修复、文档生成

任务复杂度高 + 容错空间小 → 旗舰模型（Opus / GPT-4o）
  例：架构设计、复杂重构、安全审查

需要中文优化 + 内网部署 → 国产模型（Qwen、DeepSeek）
  例：内部系统、中文密集场景、合规要求
```

### 3.4 模型升级与降级的风险

模型版本变更不是"无感升级"——它可能改变系统行为：[⁷](#ref7)

| 风险 | 说明 | 案例 |
|------|------|------|
| **输出格式变化** | 新版本的输出格式可能不同，破坏下游解析 | 模型升级后 JSON 字段顺序改变 |
| **能力退化** | 某些任务上新模型反而不如旧模型 | 新版本在某类代码生成上准确率下降 |
| **行为偏移** | 安全策略、拒绝模式、风格可能变化 | 升级后模型拒绝回答之前能回答的问题 |
| **成本变化** | 新模型可能更贵或更便宜 | 升级后 API 费用翻倍 |

> **最佳实践**：模型版本变更必须视为**破坏性变更**，需要回归测试。在 CI 中固定模型版本号，而非使用 `latest`。


## 四、多轮对话的状态局限

### 4.1 LLM 是无状态的

LLM 本身没有"记忆"——每次调用都是一次独立的推理。所谓的"多轮对话"，实际上是把**之前所有对话历史**作为输入一起发送给模型：[³](#ref3)

```
第 1 轮：用户问题 → 模型回复
第 2 轮：用户问题 + [第1轮历史] → 模型回复
第 3 轮：用户问题 + [第1轮 + 第2轮历史] → 模型回复
...
第 N 轮：用户问题 + [前 N-1 轮历史] → 模型回复  ← 上下文越来越大
```

这意味着：
- **每多一轮对话，输入 Token 数就增加**——成本线性增长
- **对话越长，早期内容越容易被"遗忘"**——上下文窗口有上限
- **模型没有真正的"记忆"**——它只是每次重新"阅读"所有历史

### 4.2 "越聊越傻"的工程后果

当对话轮数增多、上下文接近窗口上限时，会出现几个典型问题：

| 问题 | 表现 | 根因 |
|------|------|------|
| **早期遗忘** | 模型"忘记"了对话开头讨论的约定 | 早期内容被截断或压缩 |
| **指令漂移** | 开头设定的 System Prompt 约束逐渐失效 | "Lost in the Middle"效应 + 注意力稀释 |
| **前后矛盾** | 模型给出与前文矛盾的回答 | 中间内容注意力不足 |
| **重复劳动** | 模型重复之前已经讨论过的内容 | 历史信息在上下文中的权重下降 |
| **成本飙升** | 每次请求都带着完整历史，Token 消耗线性增长 | 无状态本质 |

### 4.3 应对策略

| 策略 | 原理 | 适用场景 |
|------|------|---------|
| **定期压缩对话** | 将历史对话摘要为简短总结，替换原始历史 | 长对话场景 |
| **结构化持久化** | 将关键决策、约定写入文件（如 CLAUDE.md），每次会话重新加载 | 跨会话保持一致性 |
| **新会话 + 上下文注入** | 开始新对话，只注入必要的上下文摘要 | 避免上下文膨胀 |
| **任务拆分** | 将大任务拆为独立子任务，每个子任务一个新会话 | Agent 长任务 |

> **核心认知**：不要期望 LLM 在长对话中保持完美的记忆。与其依赖对话历史，不如把重要信息**持久化到文件**，每次会话显式加载。这也是 CLAUDE.md 和 Project Rules 存在的意义——它们是**确定性的上下文注入**，不依赖模型的"记忆力"。


## 五、本节关键要点

- Token 计费分输入/输出，输出单价通常是输入的 2~5 倍，控制输出长度更省钱
- Prompt Caching 让重复的前缀内容享受折扣（Anthropic 降 90%、OpenAI 降 50%），把不变内容放前面更容易命中缓存
- 模型选型要匹配任务复杂度：轻量模型处理高频简单任务，旗舰模型处理复杂任务，不要"杀鸡用牛刀"
- 模型版本变更是破坏性变更，必须回归测试，CI 中应固定模型版本号
- LLM 是无状态的，多轮对话越长越不可靠，重要信息应持久化到文件而非依赖对话历史
