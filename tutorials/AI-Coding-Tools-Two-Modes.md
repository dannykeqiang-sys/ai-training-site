# AI Coding 工具的两种模式

如果你用过 GitHub Copilot 或 Cursor，你可能注意到了两种截然不同的交互方式：一种是你写代码时自动弹出建议，另一种是你描述需求后 AI 自主完成任务。本文解释这两种模式的原理和最佳使用场景。

> **一句话理解**：补全模式是"AI 帮你写下一行"，Agent 模式是"AI 帮你完成整个任务"。

## 一、两种核心交互模式概述

![代码补全模式与 Agent 模式对比](https://yk-ai-mentor.youku.com/yk_ai_mentor/tutorials/ch1/images/coding-two-modes_1784689052.png)

主流 AI 辅助编码工具（GitHub Copilot、Cursor、Windsurf、通义灵码等）普遍提供**两种主要交互模式**：[¹](#ref1) [²](#ref2)

| 模式 | 别名 | 典型触发方式 | 代表产品功能 |
|---|---|---|---|
| **代码补全模式（Completion Mode）** | Inline Suggestion / Ghost Text / Tab Completion | 编码时自动触发，按 Tab 接受 | GitHub Copilot Inline、Cursor Tab |
| **Agent 模式（Agent Mode）** | Chat + Execute / Agentic Mode | 用户在对话框描述需求，AI 自主规划并执行 | Cursor Agent、Copilot Agent Mode、Cline |

## 二、代码补全模式的工作原理

### 2.1 基本机制

代码补全工具的本质是一个**实时预测引擎**：[¹](#ref1) [³](#ref3)

```
用户正在编辑的代码 + 上下文信息 → 模型推理 → 生成建议 → 以"幽灵文本"显示
```

> **关键认知**：AI 编码工具生成的是**概率性建议**，不是"已验证的正确代码"。模型基于训练数据中的统计模式预测最可能的代码片段，但无法保证逻辑正确性、语法正确性或符合业务需求。

具体步骤：
1. **上下文采集**：工具收集当前光标位置的上下文信息，包括：
   - 当前文件中光标前后的代码
   - 同项目中已打开的相邻 Tab 文件内容
   - 文件路径、语言类型等元信息
2. **模型推理**：将上下文打包发送给专用补全模型（通常是经过优化的小型快速模型），预测下一段最可能的代码
3. **Ghost Text 呈现**：模型生成结果以**灰色半透明文本（Ghost Text / 幽灵文本）**显示在光标位置
4. **用户决策**：用户按 `Tab` 接受建议，或继续输入忽略建议

### 2.2 关键技术特征

| 特征 | 说明 |
|---|---|
| **触发方式** | 被动触发——用户一停顿即预测，无需手动发起 |
| **响应延迟** | 极低（通常 < 500ms），要求模型轻量快速 |
| **生成范围** | 单行 ~ 多行代码片段，不跨文件 |
| **上下文范围** | 当前文件 + 少量邻近文件（受 Token 预算限制） |
| **模型类型** | 专用补全模型（如 Copilot 使用 Codex 衍生模型，Cursor 使用自训练的 Tab 模型） |
| **执行能力** | ❌ 无——只建议代码，不能执行命令、创建文件 |

> GitHub Copilot 官方文档描述："Copilot generates dimmed ghost text suggestions at your current cursor location...it also evaluates your active changes to predict the location of the next edit."[¹](#ref1)

### 2.3 注释驱动的补全

在代码中写自然语言注释也能触发补全。例如：
```python
# 计算两个日期之间的工作日天数
def count_business_days(start, end):
    # Copilot 会根据注释生成函数体
```

这本质上仍是补全模式——模型将注释视为"前缀上下文"来预测后续代码。[¹](#ref1)

## 三、Agent 模式的工作原理

### 3.1 基本机制

Agent 模式的核心区别在于：AI 不再是被动建议者，而是**主动执行者**。[²](#ref2) [⁴](#ref4)

```
用户自然语言描述需求 → Agent 规划任务步骤 → 调用工具（读写文件、执行命令、搜索代码）→ 
观察结果 → 继续执行或调整 → 直到任务完成
```

### 3.2 Agent 模式的核心能力

| 能力 | 说明 | 示例 |
|---|---|---|
| **任务规划** | 自主将复杂需求拆解为子步骤 | "重构这个模块"→ 分析依赖 → 修改接口 → 更新调用方 → 运行测试 |
| **多文件编辑** | 同时创建和修改多个文件 | 新增 API 时同时创建路由、控制器、测试文件 |
| **终端命令执行** | 自主运行 shell 命令 | 安装依赖、运行测试、执行构建 |
| **代码搜索** | 在整个代码库中搜索相关代码 | 查找所有调用了某个被废弃 API 的地方 |
| **自我纠错** | 观察执行结果，发现错误后自动修复 | 编译报错后自动定位并修复语法错误 |

## 四、两种模式的关键差异对比

| 维度 | 代码补全模式 | Agent 模式 |
|---|---|---|
| **交互方式** | 被动——编码时自动弹出建议 | 主动——用户描述需求后 AI 自主行动 |
| **自主性** | 无自主性，只做单步预测 | 高自主性，自主规划、执行、验证 |
| **操作范围** | 单文件、光标附近 | 跨文件、全项目范围 |
| **执行能力** | 仅生成文本建议 | 可读写文件、执行命令、调用工具 |
| **上下文消耗** | 少（仅当前文件 + 邻近文件片段） | 大（整个对话历史 + 工具调用结果） |
| **延迟要求** | 极低（< 500ms），要求实时响应 | 可容忍较长等待（秒 ~ 分钟级） |
| **使用模型** | 轻量专用模型 | 大参数通用模型（GPT-4、Claude 3.5 Sonnet 等） |
| **适用场景** | 日常编码、行级/函数级补全 | 复杂重构、新功能实现、Bug 定位修复 |
| **成本** | 低（Token 少、模型小） | 高（多轮对话、工具调用、大模型） |

> **核心区别**：补全模式是"AI 帮你写下一行"，Agent 模式是"AI 帮你完成整个任务"。

### 快速决策树

```
当前任务是否需要跨文件操作或多步骤规划？
├── 否 → 补全模式（按 Tab 加速编码）
└── 是 → Agent 模式（描述需求，让 AI 自主完成）
```

## 五、实际使用场景与选择建议

![按任务规模选择模式](https://yk-ai-mentor.youku.com/yk_ai_mentor/tutorials/ch1/images/mode-selection-scene_1784689064.png)

### 5.1 何时用补全模式

补全模式适合**已知"做什么"、只需加速"写出来"**的场景：

- 日常逐行编码：写函数体、补条件判断、循环结构
- API 调用：知道要调什么接口，让 AI 补全参数和错误处理
- 重复性代码：相似的 CRUD 操作、测试用例模板
- 快速实验：在已有代码上小幅修改验证想法

> 经验数据：GitHub 官方统计，使用 Copilot 补全模式的开发者，代码编写速度平均提升 55%，任务完成时间减少 25%。[¹](#ref1)

### 5.2 何时用 Agent 模式

Agent 模式适合**需要多步骤规划、跨文件操作**的复杂任务：

- 新功能实现：从零搭建一个完整模块（路由 + 控制器 + 测试）
- 大规模重构：重命名模块、调整目录结构、更新所有引用
- Bug 调试：分析错误日志、定位问题代码、实施修复、验证通过
- 代码迁移：从 JavaScript 迁移到 TypeScript、升级框架版本
- 文档生成：基于代码自动生成 API 文档

### 5.3 成本与效率的权衡

| 维度 | 补全模式 | Agent 模式 |
|---|---|---|
| **Token 消耗** | 少（仅当前文件 + 邻近文件片段） | 大（整个对话历史 + 工具调用结果） |
| **API 成本** | 极低（专用小模型或本地模型） | 较高（大模型 + 多轮调用） |
| **人工介入** | 低（按 Tab 即可） | 中等（需要确认关键操作） |
| **最佳 ROI 场景** | 高频、小粒度编码 | 低频、大粒度复杂任务 |

## 常见误解


- ❌ "编译模式和解释模式"——这是编程语言运行方式，与 AI 工具无关
- ❌ "训练模式和推理模式"——这是模型生命周期概念

- ❌ "从代码模板库中匹配"——补全是**生成式**的，不是模板匹配
- ❌ "把整个项目发送给模型"——受 Token 限制，只发送精选的上下文片段

- ❌ "Agent 模式不需要大模型"——Agent 的核心仍是大模型驱动
- ❌ "补全模式比 Agent 模式更准确"——准确性取决于任务类型和上下文质量
